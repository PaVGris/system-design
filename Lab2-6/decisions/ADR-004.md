# ADR-004: Redis как кеш для токенов и каталога товаров

## Контекст и мотивация

При каждом запросе api-gateway обращается к user-service для валидации токена (`GET /users/validate`). Это синхронный HTTP-запрос, который в свою очередь делает SQL-запрос в PostgreSQL. При высоком трафике это создаёт узкое место: N входящих запросов → N HTTP round-trips → N SQL-запросов.

Аналогично, `GET /items` при каждом вызове читает всю коллекцию из MongoDB, хотя каталог меняется редко.

## Решение

Добавить Redis как кеш в два сервиса:

**user-service** — кешировать маппинг `token → user_id` с TTL 1 час.  
**item-service** — кешировать полный список товаров (`items:all`) с TTL 5 минут и явной инвалидацией при изменениях.

## Причины выбора Redis

- Встроенная поддержка в userver через `components::Redis` и `storages::redis::ClientPtr`
- TTL из коробки — `EXPIRE` / `SET ... EX`
- Атомарный `INCR` — основа для rate limiting без локов
- `allkeys-lru` eviction — Redis деградирует до обычного кеша при нехватке памяти, не ломает систему

## Ограничения

- Redis — кеш, не источник истины. При его падении сервисы переключаются на БД (graceful degradation реализован через try/catch с fallback).
- Кеш токенов хранит `user_id` как строку — при изменении роли пользователя (если добавить такую операцию) потребуется явная инвалидация всех токенов пользователя.
- Один экземпляр Redis — single point of failure. Для production нужен Redis Sentinel или Cluster.
